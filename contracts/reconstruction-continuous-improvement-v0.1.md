# Reconstruction Continuous Improvement Contract v0.1

## Status
Orchestration-approved lifecycle boundary for GPT-6 reconstruction improvement. Reviewed outcomes may become versioned improvement evidence without changing Core, StructuralDetectionEvidence, or StructuralLayoutProposal semantics. This contract does not activate autonomous production self-modification or bypass human review.

## Ownership
GPT-6 owns reconstruction feedback ingestion, improvement-case preparation, versioned benchmarks, candidate reconstruction changes, evaluation evidence, and rollback artifacts. GPT-7 remains owner of source-page detector evidence/training; GPT-6 improvement artifacts MUST NOT become StructuralDetectionEvidence, detector annotations, or detector ground truth. GPT-4 owns cross-repository orchestration and Core compatibility reconciliation. GPT-5 retains security ownership.

## Improvement principle
Continuous improvement MUST be evidence-driven and versioned. A user correction, reviewer decision, project outcome, or GPT-6 proposal MUST NOT automatically become a permanent reconstruction rule. Feedback is evaluation evidence, not engineering truth by itself. Candidate changes may affect GPT-6-private heuristics, ranking, thresholds, fusion logic, review routing, or proposal strategy only when active contracts remain valid and promotion gates pass.

## Improvement case
An improvement case SHOULD retain `case_id`, `source_id`, `page_id`, `project_group_id`, input contract versions, source/page provenance, coordinate-space/transform chain, detector evidence references when used, original GPT-6 output, reviewer correction/adjudicated outcome, correction category, affected object types, rationale/evidence references, review state, timestamps, and benchmark eligibility. Secrets and unrelated user data MUST NOT be stored.

Eligible evidence includes reviewed grid reconstruction, corrected column/beam/wall proposal geometry, topology/connectivity, scale/transform decisions, observed/reconstructed/proposed classification, review-routing failures, and repeated false/missed proposal patterns across independent projects. A single correction MUST NOT establish a universal rule.

## Forbidden learning shortcuts
GPT-6 MUST NOT learn/promote that every grid or beam intersection creates a column; regular spacing alone proves geometry; missing GPT-7 detection proves absence; a GPT-6 proposal is visible source evidence; an architectural partition is structural from graphics alone; reviewer approval retroactively creates StructuralDetectionEvidence; or synthetic overlays become source provenance by reprocessing through GPT-7.

## Versioned reconstruction benchmark
GPT-6 MUST maintain versioned/frozen reconstruction benchmarks rather than mutate released evidence. Coverage SHOULD include no-grid, no-visible-column, incomplete/ambiguous grids, column/beam/wall detector evidence, missing/conflicting evidence, scale-confirmed/unresolved sources, topology ambiguity, multi-page/level consistency when applicable, observed/reconstructed/proposed semantics, provenance/transforms, Core writeback eligibility, and legacy detector compatibility. Project-group isolation SHOULD be used where related drawings could cause leakage.

## Candidate improvement
Every candidate MUST record base commit, candidate commit, motivating improvement cases, benchmark version, configuration/threshold changes, evaluation results, and known regressions/limitations. A candidate MUST NOT silently rewrite GPT-2-owned engineering calculation logic.

## Promotion gate
A candidate MUST NOT automatically replace active GPT-6 behavior. Promotion requires:
1. all active GPT-6 contract tests pass;
2. StructuralLayoutProposal v0.1 semantics remain valid;
3. StructuralDetectionEvidence v0.2 consumer compatibility remains valid;
4. legacy v0.1 column/beam compatibility and v0.1 wall rejection remain valid;
5. evaluation on a frozen/versioned reconstruction benchmark;
6. no unresolved critical regression in known failure modes;
7. provenance and source/transform traceability remain intact;
8. unapproved proposals remain ineligible for canonical Core writeback;
9. approved proposals still require Core mapping/validation;
10. compatibility with the latest released Core Contract;
11. no direct PyNite dependency across the platform boundary;
12. human/admin approval;
3. documented rollback target.

## Evaluation and rollback
Baseline and candidate MUST be compared on the same frozen benchmark. Reports MUST expose regressions as well as improvements; aggregate gains MUST NOT hide critical contract/safety regressions. Task-specific metrics or deterministic case-level pass/fail evidence may be used.

Every promotion MUST record promoted commit, previous active commit, benchmark version, evaluation artifact, approval evidence, Core Contract version/SHA, active detector/proposal contract versions, and rollback target. Historical benchmark/review evidence MUST remain immutable.

## StructuralLayoutProposal and GPT-7 boundaries
Continuous improvement may improve how GPT-6 creates, ranks, validates, or routes StructuralLayoutProposal records, but MUST preserve `observed`, `reconstructed`, and `proposed`. Proposed records remain non-canonical until review and Core-writeback gates pass.

GPT-6 improvement evidence is not GPT-7 ground truth. A possible missing source observation discovered during GPT-6 review may enter GPT-7 datasets only through GPT-7 independent source-evidence/adjudication and dataset policy.

## Core and PyNite boundary
This lifecycle contract is not a Core schema. Canonical writeback MUST use the latest released Core Contract. PyNite MUST be reached only through the Core analysis adapter. Continuous-improvement code MUST NOT introduce direct PyNite dependency.

## Required implementation/regression coverage
Before runtime activation, GPT-6 MUST demonstrate:
1. single corrections cannot automatically create universal rules;
2. improvement cases preserve source/page provenance;
3. project-group identity supports benchmark isolation;
4. proposed and observed evidence remain distinguishable;
5. zero detector observations do not prove engineering absence;
6. grid intersections do not automatically create columns;
7. synthetic overlays cannot manufacture detector provenance;
8. candidate changes cannot auto-promote;
9. frozen benchmark comparison reports regressions;
10. unapproved proposals cannot write Core geometry;
11. approved proposals still require Core mapping/validation;
12. StructuralDetectionEvidence v0.2 regressions remain passing;
13. StructuralLayoutProposal v0.1 regressions remain passing;
14. legacy v0.1 compatibility/wall-rejection regressions remain passing;
15. latest Core compatibility is checked before promotion;
16. no direct PyNite dependency is introduced;
17. rollback target is required for promotion.

## Activation
Contract definition is orchestration-approved. Runtime continuous improvement is NOT active until GPT-6 implements feedback/improvement-case representation, frozen/versioned benchmark workflow, candidate evaluation and promotion/rollback gates, required regressions, CI evidence, and project-status evidence. No autonomous production self-modification is authorized.
